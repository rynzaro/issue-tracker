Warum ein Action-Layer und ein Service-Layer?

In einem Satz: Actions sind die Sicherheitsgrenze, Services sind die Geschäftslogik. Actions kümmern sich um alles, was nur das Web-Framework wissen kann (wer eingeloggt ist, wie der rohe Input aussah, welche Seiten revalidiert werden müssen); Services stellen sicher, was fachlich gelten muss (Ownership, Kaskaden, Transaktionen, Invarianten) — und bleiben genau deshalb testbar und wiederverwendbar. Fluss nach AF-3: Component → Server Action → Service → Prisma. Es gibt keine REST-API-Routen für die App selbst — Server Actions ersetzen sie für Mutationen, und Server Components lesen direkt über Services. API-Routen existieren nur für externe Integrationen.

Vorteile

Auth wird genau einmal geprüft — am Eintrittspunkt
Jeder Session-Check liegt in einer Action oder Server Component — eine einzige, auditierbare Stelle pro Operation statt defensiver Checks quer durch die Datenschicht.
Services komponieren reibungslos
deleteProject kann die Task-Kaskaden-Logik aufrufen, Checkpoint-Services rufen Task-Services — ohne wiederholtes Auth-Zeremoniell, ohne zirkuläres Session-Plumbing.
Geschäftslogik ist unit-testbar
Services sind einfache async-Funktionen. tests/unit/services/ testet Kaskaden und Hierarchie-Policy gegen eine DB, ohne auth() oder die Next.js-Runtime zu mocken.
Framework-Belange bleiben isoliert
"use server", auth() und revalidatePath() existieren nur in Actions. Die Services würden einen Umzug zu API-Routen, einer CLI oder einem Cron-Job unverändert überstehen.
Ein Fehler-Contract von Ende zu Ende
Alles gibt eine ServiceResponse zurück — das UI rendert Erfolgs- und Fehler-Toasts einheitlich, und keine rohe Exception erreicht den Client.

Nachteile

Boilerplate pro Operation
Jede Action wiederholt dieselben ~20 Zeilen: Session-Check, zod-Parse, Delegation, Revalidierung. project.actions.ts besteht aus fünf fast identischen Wrappern.
Sicherheit per Konvention, nicht per Compiler
Nichts hindert eine neue Action daran, auth() zu vergessen, und nichts hindert Code daran, einen Service mit der falschen userId aufzurufen. AD-18 warnt Reviewer explizit: fehlende Checks in Services sind Absicht — dieses Wissen muss jedes Review mittragen.
Indirektionskosten bei trivialem CRUD
Ein einzeiliges Prisma-Update berührt trotzdem drei Dateien (Schema, Action, Service). Bei simplen Reads bringt der Wrapper kaum mehr als den Auth-Check.
Die Grenze ist unschärfer als der Slogan
Services machen keine Authentifizierung, aber sie erzwingen Ownership — updateProject vergleicht project.userId mit der übergebenen userId. Die ehrliche Regel lautet „kein Session-Zugriff unterhalb der Linie“, nicht „keine Sicherheit unterhalb der Linie“.

Bewusste Grenze → geplante Erweiterung (AD-20)

Die Nachteile links sind bekannt und dokumentiert — die Weiterentwicklung ist bereits entschieden: Ein zentrales, handgeschriebenes Policy-Modul (lib/authz/policy.ts) mit can(principal, action, resource), das Autorisierung an die Service-Grenze verlagert. Actions bleiben die Authentifizierungsgrenze; Services laden die Ressource und prüfen dann selbst. Damit wird „Services komponieren frei ohne Auth-Recheck“ bewusst aufgegeben — diese Eigenschaft funktioniert nur, solange das Berechtigungsmodell flach ist (ein Principal, binäres Ownership). Sobald Team-Modus (AD-13/AD-15) Rollen einführt, kann ein roher userId-String Autorität nicht mehr ausdrücken. Status: entschieden, noch nicht implementiert — ARCHITECTURE_DECISIONS.md → AD-20.
