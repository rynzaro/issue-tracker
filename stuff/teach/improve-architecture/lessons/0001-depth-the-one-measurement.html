Depth — the one measurement

Lesson 1 · ~10 minutes · reads your own task.service.ts

Why this lesson: your architecture reviews rank everything by one idea — depth. If you can measure depth yourself, you can rank refactors yourself. That is the mission.

The idea

A module has two sizes: the size of its interface (everything a caller must know) and the size of its implementation (everything it does). Depth is the ratio.

This is John Ousterhout's core claim: the point of a module is to hide complexity. A shallow module makes you learn an interface but hides nothing in return — it adds cost without paying anything back.

The deletion test — the fastest depth probe. Imagine deleting the module. If the complexity just vanishes, it was a shallow pass-through. If the complexity reappears, copied into every caller, the module was deep — it was earning its keep. (glossary)

Now look at your own code

Open lib/services/task.service.ts. Six functions — delete, complete, uncomplete, archive, unarchive, restore — each re-type the same sequence: load → auth → validate → timer guard → plan → execute.

Run the deletion test in reverse: the deep module (applyTransition) does not exist yet, so its implementation is already living "copied into every caller" — six times. The completeTask/archivedAt bug from your review exists only because there are six copies of the load step. That is what missing locality looks like: one fix needed six times.

Contrast: taskHierarchyPolicy.ts passes the deletion test. Delete it, and ancestor-legality rules reappear in every mutation. It is deep — small interface (validateTransition), 280 lines of rules and a 401-line test behind it.

Primary source

Watch Ousterhout — “A Philosophy of Software Design”, Talks at Google (2018). One hour; the deep/shallow section is the heart of it. His book of the same name (2nd ed.) is the course backbone if you want more.
