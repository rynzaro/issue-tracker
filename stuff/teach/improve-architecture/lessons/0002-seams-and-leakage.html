Seams — and what leaks across them

Lesson 2 · ~10 minutes · reads your own tasks.tsx and lib/util.ts

First, from memory (no peeking at Lesson 1): what does the deletion test ask? Say it out loud, then check the glossary. Retrieval like this is what makes it stick.

The idea

A seam is a spot in the code where what actually runs is decided somewhere else — by what a caller passes in, what adapter is plugged in, what data arrives. You can make that spot behave differently (a test passes a fake, production passes the real thing) without ever editing the spot itself. That is where a module's interface lives. The term is Michael Feathers'. Your biggest seam is server → client: everything the server hands the client is interface, whether you meant it or not.

Leakage (Ousterhout: information leakage) is when implementation knowledge shows up on the caller's side of the seam. The caller now depends on how the module works, not just what it answers. Change the how, and code beyond the seam breaks — the whole point of the module is defeated.

The quick probe: who recomputes? If a caller recomputes something the implementation already knew, the seam leaks. The knowledge crossed in a shrunken form, and the caller had to grow it back.

Leak 1 — the boolean that used to be a Date

Open lib/services/project.service.ts:302-314. The server walks the whole task tree, post-order, and while doing so it knows which descendant timer is running and when it started. Then it ships only hasActiveDescendant: boolean (lib/schema/task.ts:51).

Now open app/s/project/[project-id]/tasks.tsx:86-91: the client needs that start Date after all — so it calls getActiveDescendantStartedAt (lib/util.ts:120-131), which re-walks the subtree to recover what the server threw away.

server:  walks tree, knows Date  →  ships boolean   ✂ answer shrunk
client:  needs Date              →  walks tree again ↻ leak made visible

The client now contains tree-traversal knowledge — pure implementation. If the server changes how activity is derived (say, multiple timers), lib/util.ts silently disagrees. Same disease as Lesson 1's six loaders: one fact, two owners. Fix: nodes carry activeDescendantStartedAt: Date | null — the seam ships the full answer, and the client function gets deleted.

Leak 2 — the type that snuck into the interface

archiveTaskList.tsx:4 (a 'use client' file) imports TaskParentInfo from project.service.ts:460. A service-internal type is now part of the client's world — nobody decided that; an import made it so. Reshape the service's internals and a client file breaks. That's the definition of leakage: the seam grew without a design decision.
