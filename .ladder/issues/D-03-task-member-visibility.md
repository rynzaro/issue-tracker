# D-03 — Task Member visibility scope

**Status:** RESOLVED 2026-07-23 — Option A

## Context

Once membership attaches somewhere (D-02) and execution is creator-exclusive
(D-04), the open question is what a Task Member can *see*: the full project
tree, only the host subtree, or the host + its ancestors for context.

Facts:
- Visibility is the structural/visibility authority family — the one place
  FUTURE_COLLABORATION's "project membership = task access" claim survives
  AUTHORIZATION_PLAN (§7 conflict 1: holds for structural/visibility only).
- A checkpoint is a cross-section of a task + its **direct children**
  (CONTEXT.md; invariant 3). A member creating children under the host feeds
  the host's parent checkpoint. So visibility is not just a UI question — it
  determines which `CheckpointTask` rows a member's actions generate and who
  can read them.
- Scoped repos (FUTURE_COLLABORATION Phase 1 prereq) are the data-isolation
  half; the policy module (D-01) is the act-permission half. Both feed this.

## Decision

What subtree is visible to a Task Member, and is the host task's parent
(whose checkpoint the member's subtasks land in) visible to them?

## Options

- **A. Host subtree only.** Member sees the host task + descendants. Cheapest
  mental model; matches "added to a specific task." But the member never sees
  the host's parent, so the project tree is fragmented for them.
- **B. Host subtree + ancestor chain (read-only).** Member sees the path root→host
  (read) and host→descendants (their subtree, full authority on their own
  created part). Gives context without leaking siblings.
- **C. Full project tree, member-shaped authority.** Member sees everything,
  acts only on their subtree. Simplest query; leaks sibling work and other
  members' evidence — collides with the estimation-evidence-privacy principle.

## Resolution (2026-07-23)

**Option A — host subtree only.** A Task Member sees the host task and its
_descendants_. No ancestors, no siblings, no other project tasks. This matches
"added to a specific task" literally and keeps the data-isolation boundary
minimal: what a member's actions touch is what they may read.

Consequences:
- `CheckpointTask` rows generated by a member under the host feed check-points
  the member can read because they are inside the host subtree.
- The host's parent checkpoint is **not** readable by the member — but the
  member's children still appear in it as facts. This is a read/view asymmetry:
  a member can write children that become columns in a cross-section the member
  cannot open. D-05 must decide who owns that cross-section.
- Scoped-repository work for Task Member can scope reads to `taskId IN (hostId
  UNION descendants)`; no project-level visibility rule is needed.

## Blocking edges

- **Blocks:** D-05 (checkpoint readability + which cross-sections a member
  generates), D-08 (analysis scope).
- **Blocked by:** D-01 (scoped repos / policy), D-02 (membership anchor).
